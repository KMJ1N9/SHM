### 1.2 API 通信层 — 双 Token 无感刷新

> "我封装了统一的 HTTP 请求层，所有接口调用只需一行代码，Token 管理、过期刷新、错误拦截全部在底层自动处理。"

核心设计：

```
业务代码:  await get('/orders', params)
              ↓
request() 统一入口
  ├─ 自动附加 Bearer Token
  ├─ code=0 → 返回 body.data
  ├─ code=1002 → 自动刷新 Token → 重试原请求
  │    └─ 并发控制: isRefreshing + refreshQueue 排队
  ├─ code=1001 → 跳登录页
  ├─ code=1003 → 被踢下线
  ├─ code=1004 → 账号封禁
  └─ 网络异常 → 中文提示
```

**亮点**：多个请求同时过期时，只有第一个去刷新 Token，其余排队等待，刷新完批量重试——避免并发刷新导致 Token 错乱。

**展示建议**：打开 `api/index.js`，展示 `request()` 函数中 `isRefreshing` + `refreshQueue` 的并发控制逻辑。

## 可能被问的问题

**Q：Token 无感刷新怎么实现的？多个请求同时过期怎么办？**
> 拦截器检测到 code=1002 时，如果当前没有刷新在进行中（`!isRefreshing`），就调用 refresh 接口；如果已有刷新在进行中，就把这个请求的 resolve/reject 推到 `refreshQueue` 队列里，等刷新完成后统一重试。这样 10 个请求同时过期只会发 1 次刷新请求。

**Q：怎么判断用户能不能发布/交易？**
> Pinia store 里有 `canPublish`（信誉分 >= 60）和 `canTrade`（信誉分 >= 30）两个 getter。发布页和下单前都会检查，不满足条件直接弹 toast 拦截。

**Q：订单状态怎么流转的？**
> pending → met_pending（一方发起面交）→ met（另一方确认）→ completed（买家确认收货）。任一方可在 pending/met_pending 取消。面交是双向确认：发起方不能自己确认，双方同时发起自动完成。

**Q：首页性能怎么优化的？**
> 游标分页代替传统 offset 分页，避免大页码扫描；商品图片懒加载；分类筛选在客户端做（已加载的数据内过滤）；双列瀑布流只渲染可见区域附近的内容。

**Q：26 个页面怎么管理的？**
> uni-app 的 pages.json 统一管理路由，TabBar 页用 switchTab，子页面用 navigateTo。easycom 自动注册通用组件，不用手动 import。
